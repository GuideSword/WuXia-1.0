# 武侠撤离式 RPG Web MVP 设计

## 1. 目标与验证标准

本项目制作一款面向手机竖屏用户的单机 Web 游戏，类型为“文字冒险 + 武侠 RPG + 撤离式玩法”。第一版必须完整覆盖 Phase 1～7，并通过一条高密度的“青石镇—黑风寨—血刀经”纵切线验证三个问题：

1. 玩家取得重要物品后，是否会认真权衡立即撤离与继续深入。
2. 玩家学会新武学后，是否愿意重返旧地图尝试新路线。
3. 玩家失败并失去本局所得后，是否仍愿意再次入局。

成功标准是可在手机浏览器中连续完成“探听、整备、入局、搜索、战斗、取得目标、权衡、撤离、结算、参悟、再次入局”，且三类核心抉择均由实际规则支持，而不是只出现在文案中。

## 2. 范围

### 2.1 首版必须完成

- 一个安全区域“青石镇”，含客栈、茶馆、药铺、黑市、练功地点。
- 一个危险区域“黑风寨”，含山脚、山门、仓库、牢房、二当家房间、寨主密室、后山、水道。
- 10 名实际参与对话、交易、战斗、情报或关系玩法的 NPC。
- 6 门实际影响玩法的武学：基础剑法、狂刀、太极剑、燕回身、龟息功、点穴。
- 20 条可获得、确认或消费的情报。
- 10 种可购买、携带、使用、失去或结算的道具。
- 5 条撤离路线：山门、悬崖、水道、商队、后山密道。
- “血刀经残页 → 寨主密室线索 → 血刀门传人位置”的主要获取链。
- 无账号本地自动存档，以及 JSON 存档导入、导出。

### 2.2 明确不做

不制作大世界、完整门派体系、经脉、转生、轮回、PvP、联机、公会、装备强化、宠物、坐骑、数百武学或 NPC，也不制作开放世界实时 AI 模拟。首版不需要后端、登录系统或云存档。

## 3. 技术方案

使用 React、TypeScript 和 Vite 构建静态单页 Web 应用。规则与内容保持框架无关：React 负责渲染和派发玩家动作，纯 TypeScript 规则引擎负责判断可用选项、执行效果和生成下一状态。内容通过 JSON 配置，Zod 在启动时做运行时校验。

测试采用 Vitest、React Testing Library 和 Playwright。游戏可部署到任意静态托管服务，首版不引入服务端依赖。

## 4. 状态架构

游戏拥有永久层与本局层，两者只能通过明确的入局和结算操作交换数据。

### 4.1 永久层

永久层保存在浏览器本地，包含：

- 已学会的武学和已完成的参悟。
- 已确认的重要情报与主线确认节点。
- 仓库道具、永久银两和已解锁地点。
- NPC 关系成果与长期统计。
- 当前可追查目标和已经开启的后续线索。

### 4.2 本局层

进入黑风寨时，从永久层选择携带内容并创建本局状态。本局层包含：

- 当前地点、气血、药品、负重和携带银两。
- 风声、区域警戒阶段、目击者和已触发事件。
- 本局临时战利品、未撤离秘籍和未确认情报。
- 敌人状态、战斗回合、当前可用撤离路线。

### 4.3 提交边界

成功撤离时，本局战利品、秘籍、银两和情报按照结算规则合并到永久层。死亡或被擒时，本局普通战利品和未保存秘籍丢失；已学武学、已确认重要情报、既有关系成果和已经提交的核心剧情节点保留。

入局、事件选择、战斗回合和结算都是稳定节点。动作一经提交便不能通过浏览器返回键撤销或重复领取。

## 5. 单局玩法规则

### 5.1 探听与整备

玩家在青石镇获得带有来源、可信度、目标地点、可能价值和潜在危险的情报。选定追查目标后，玩家携带武器、药品、工具和银两入局。

所有携带物都有重量。负重越高，部分身法效果越弱，悬崖等撤离路线的成功条件越苛刻。首版不引入复杂格子背包，只显示总负重、上限和每件物品重量。

### 5.2 事件与搜索

地图由地点节点和连接关系组成。进入地点后，事件引擎根据游戏状态、已知情报、时段、风声、道具、武学标签和既往选择生成 2～4 个合法动作。

搜索不是打开宝箱。事件动作包括询问、偷听、观察、潜入、战斗、使用工具、使用武学能力、取得目标、留下物品与撤退。隐藏动作只有在条件满足时显示，并明确标出触发来源，例如“伏上屋梁【燕回身】”。

### 5.3 风声

风声范围为 0～100，不随真实时间自动增加。被发现、战斗、杀人、偷窃、闯入禁区、触发机关、放跑目击者和使用显眼武学会增加风声。

- 0～24：区域正常。
- 25～49：增加巡逻，部分 NPC 警觉。
- 50～74：出口盘查，高阶 NPC 开始行动。
- 75～99：高度警戒，普通路线关闭。
- 100：全面追捕，首领加入追捕。

事件后果必须预告可合理感知的风险，例如“风声可能大幅增加”，但不必总是公开精确数值。

### 5.4 战斗

战斗为轻量回合制。每回合可选择普通攻击、武学招式、防御、身法、道具或撤退。敌人的下一步意图及主要标签可读，例如“蓄势【刚】【爆发】”。

武学招式通过标签关系获得额外效果。首版只实现少量清晰关系，例如【柔】可卸【刚】、【后发】在正确判断先手攻击时触发反击、【位移】可规避锁定攻击。数值决定基础结果，判断正确提供足以改变战局的优势。

### 5.5 武学

武学不设复杂等级。每门武学拥有 2～4 个能力标签，并可同时挂接三类能力：

- 战斗招式与标签反应。
- 地图事件中的特殊动作。
- 撤离路线或身份判断条件。

例如燕回身提供闪避、屋顶入口和悬崖撤离；龟息功提供水下调查和水道撤离；点穴提供控制招式和无声制服选项。取得秘籍只是开始，玩家必须成功撤离并在青石镇参悟后才能永久学会。

### 5.6 撤离

撤离不是倒计时按钮。每条路线有独立条件与风险：

- 山门：无先决条件；风声达到 50 后出现重兵盘查。
- 悬崖：需要【轻功】能力；高负重会降低成功率或要求丢弃物资。
- 水道：需要【龟息】能力；隐蔽但可能损失部分普通物资。
- 商队：消耗银两且要求风声低于 50，可通过伪装离开。
- 后山密道：需要地图情报或特定 NPC 关系。

取得《血刀经·残页》后，玩家已经达成主要目标；继续进入寨主密室可得到传人位置，但会将风声推入高度警戒并改变出口状态。该节点是首版核心“贪或撤”验证点。

## 6. 手机端体验与美术方向

### 6.1 页面流

单页应用按六个场景切换：青石镇、情报、整备、探索、战斗、撤离结算。主动作放在屏幕下半部的拇指热区，交互目标高度不小于 44 CSS 像素，不依赖悬停、右键或横屏。

探索页采用“场景与阅读各占一半”的竖屏构图。风声、气血、负重和主要目标靠近当前选择；完整行囊、地图、局势和日志通过底部抽屉查看。浏览器返回键只关闭抽屉或回到可安全返回的查看页，不撤销已提交事件。

### 6.2 视觉语言

美术方向为“朱印侠录”：墨黑与旧纸色构成阅读底色，朱砂色只用于风声、危险、追捕和关键撤离操作，金褐色用于武学、情报和永久收益。

地点和关键获得时刻使用 AI 生成的竖屏武侠场景图。图片负责地域、天气、光影与危险氛围；所有正文、数字、按钮和图标由前端独立渲染。场景图中央和下部保留低细节区域，并叠加墨色渐隐，确保文字对比度。首个视觉基准是“黑风寨西仓·雨夜潜入”：冷蓝月色、湿石路、山寨灯火与小比例侠客剪影。

AI 生成图不得包含 UI、标题、可识别文字、徽标或水印。正式采用前需检查错误文字、现代物件、建筑时代感和移动端裁切。

### 6.3 动效与反馈

动效服务于状态变化：风声跨阶段时使用短促朱砂扩散与音效提示；获得秘籍时使用克制的卷页展开；撤离路线关闭时在路线列表中显示原因。尊重系统“减少动态效果”设置，不用持续晃动或高频闪烁制造紧张。

## 7. 数据驱动内容

内容文件至少包括 `locations.json`、`events.json`、`npcs.json`、`martial-arts.json`、`items.json` 和 `rumors.json`。所有实体使用稳定字符串 ID，跨文件只能通过 ID 引用。

事件配置只描述：显示条件、文案、动作、动作条件、风险提示和受支持的效果类型。JSON 不执行任意代码。复杂规则由 TypeScript 中具名、可测试的效果处理器实现。

启动校验包括：

- 必填字段和枚举值正确。
- 同类实体 ID 唯一。
- 所有跨文件引用存在。
- 地点连接可达，至少存在一条初始撤离路线。
- 事件动作引用的效果处理器和条件处理器存在。
- 奖励、重量、气血和风声变化在允许范围内。

开发环境在校验失败时报告文件、实体 ID 和字段路径。正式构建不加载半坏数据，而显示安全错误页和可导出的诊断信息。

## 8. 存档与错误处理

存档包含 `schemaVersion`、永久层、可恢复的本局稳定节点、设置和统计。每次稳定节点先写入临时键，校验可读后再替换 `current`，并保留 `lastKnownGood`。

导入流程先解析 JSON，再验证版本和结构，在内存中执行迁移，最后由玩家确认替换。任一步失败都不修改现有存档。导出文件不包含设备信息或其他隐私数据。

异常时使用中文提示说明发生了什么，并提供适用的“恢复上一存档”“导出诊断”“返回标题”或“重新开始”操作。任何解析、迁移或内容错误都不得静默清空本地进度。

## 9. 测试策略

### 9.1 规则单元测试

使用 Vitest 覆盖：

- 风声的四个阶段与 100 点追捕状态。
- 负重对行动和撤离条件的影响。
- 战斗标签关系、敌方意图和撤退。
- 五条撤离路线的开放、关闭与代价。
- 成功结算与死亡结算的保留项。
- 同一随机种子、状态和动作产生同一结果。
- 内容 Schema、引用完整性和存档迁移。

### 9.2 组件测试

使用 React Testing Library 验证手机端关键状态、禁用动作原因、敌方意图、结算所得、错误提示、底部抽屉和触控目标。

### 9.3 完整流程测试

使用 Playwright 的手机视口至少跑通：

1. 探听目标、整备入局、取得残页、成功撤离、参悟并再次入局。
2. 继续进入密室导致高风声，再通过悬崖成功撤离。
3. 探索死亡后丢失本局物资，同时保留已学武学与确认情报。
4. 刷新恢复稳定节点，导入坏存档不会覆盖当前进度。

## 10. 实施边界与顺序

实现保持规格定义的七个阶段顺序，每个阶段结束时应用必须仍可启动并完成当时已有的闭环：

1. 安全区、出发、危险区、撤离、结算。
2. 搜索与战利品。
3. 风声系统。
4. 简单战斗。
5. 武学。
6. 特殊撤离路线。
7. 情报与秘籍获取流程，以及最低内容量填充。

工程只为首版现有规则建立扩展点，不预建门派、公会、联机或大世界框架。每阶段优先完成规则和自动化测试，再连接竖屏 UI 和内容配置。
